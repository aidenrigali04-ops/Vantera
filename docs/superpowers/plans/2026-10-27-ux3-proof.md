# UX-3 — Proof Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Results proves the product works from the account's own rows — an always-visible eight-stage count funnel, a lead-source table (signal kinds + intent watch targets) and agent rows that reconcile to the funnel — plus the proof-adjacent gaps the spec lists: Playbook funnels + activity feed, the deal-size tile, safety caps shown truthfully in the sequence and Senders pages, and an Intent agent edit route.

**Architecture:** One pure module `apps/web/src/lib/proof/` builds every number from lead-level rows (`leads`, `outreach_sends`, `replies`, `lead_signals`, `intent_observations`, the intent agent's watch config); one RLS-scoped loader fetches those rows with no accountId anywhere; Results and Playbook both render from it. Caps come from `@vantera/jobs/pipeline/safety-limits` in server components and are passed to client components as plain numbers. No migration.

**Tech Stack:** Next.js App Router (RSC + server actions), Supabase JS (RLS), Vitest, Tailwind + the rule-07 app-surface tokens (`components/app/surface.tsx`, `components/ui/panel.tsx`, `components/ui/kpi.tsx`).

**Spec:** `docs/superpowers/specs/2026-10-21-activation-ux-gojiberry-gap-design.md` §3.5, §3.6 (Playbook funnels + activity feed), §3.8 (deal-size tile, caps in sequence UI, Senders import fix), §5 "UX-3 — Proof". Gate: *source table numbers reconcile to the funnel totals (test); counts computed from the account's own rows only (guardrail, same posture as ML-2).*

## Global Constraints

- **No migration.** Everything is computed from existing tables; `leads.agent_id` stays deferred (spec §8).
- **Own rows only.** Every loader takes exactly one parameter, the session's `SupabaseClient`; no function in `lib/proof/` accepts or filters by an account id (guardrail test: arity 1 + source scan for `account_id`/`accountId`).
- **Stage definitions (fixed):** Found = all `leads` rows; Qualified = `status in (qualified, enriched, in_campaign, replied, converted)`; Contacted = distinct lead ids in `outreach_sends` ∪ `leads.linkedin_invited_at not null`; Accepted = `linkedin_connected_at not null`; Replied = distinct `replies.lead_id`; Interested = distinct `replies.lead_id` with `classification = 'interested'`; Meetings = `meeting_booked_at not null OR status = 'converted'`; Closed = `status = 'converted'`. Conversion % = count ÷ previous stage, `null` when the previous stage is 0; never clamped (a stage may exceed its predecessor; the UI explains why in one line).
- **Row caps:** each lead-level fetch is capped at **5000** rows (`PROOF_ROW_CAP`); if any fetch hits the cap the view model carries `capped: true` and the surface shows "Showing the first 5,000 prospects".
- **Source rows:** one row per distinct `lead_signals.kind` (label via `signalKindLabel`, `follow` → "Follows") and one row per intent watch category (Keywords · Competitors · Creators · Hashtags) matched from `intent_observations.watch_target` against the live intent agent's `config.watch`; targets no longer in the config fold into "Removed watch targets"; leads with no signal and no observation fall into "No signal captured". A lead counts **once per row** it belongs to. Surface states: "A prospect with several signals counts once in each row."
- **Agent rows:** Scout = `leads.source = 'discovery'`; Intent = `source = 'intent'`; Added by you = `manual, import, inbound, ad`; Outreach = every Contacted lead (its Found cell shows "—").
- **Dollars gate only dollars:** the count funnel, source table and agent rows always render once `Found > 0`; the four $ KPIs + RenewalBar render only when `hasValue && roi.hasSpend`; otherwise one inline line with a link, never a full-page gate.
- **Caps are the code's caps** (rule 07): the UI never hardcodes 100/25/20 or the ramp; client components receive numbers as props; `@vantera/jobs` is imported only in server components/modules.
- Copy: sentence case, plain words, no vendor names; help article per changed surface in the same PR (rule 09); nothing under `apps/web/src/app/onboarding/`.
- Files ≤ ~250 lines; split by stage (rule 13). Tests colocated.

## Review Focus

1. **Replies without sends** (replies imported/inbound before any outreach): Replied > Contacted → funnel renders, conversion shows as `null`/"—", no negative widths, one explanatory line. Test in Task 1.
2. **Removed watch target**: an `intent_observations.watch_target` no longer present in `agents.config.watch` → counted under "Removed watch targets", never dropped. Test in Task 1.
3. **Same-kind duplicates**: a lead with two `funding` signals and one `intent` → counts once in Funding, once in Buying intent; `No signal captured` excludes it. Reconciliation: union of all source rows' lead sets per column == funnel total. Test in Task 1.
4. **Deal-size input**: empty, non-numeric, negative, > $10,000,000, and a non-admin submit → rejected with a plain message; valid → cents stored, `/today` + `/dashboard` revalidated, tile disappears. Tests in Task 5.
5. **Intent edit by a non-admin / stale agent**: `updateIntentAgent` with 0 rows → "Only an admin can change this agent."; the wizard's edit mode pre-fills every watch list and the schedule exactly. Tests in Task 6.

```ts
// types.ts
export const PROOF_ROW_CAP = 5000;
export type ProofStageKey = "found"|"qualified"|"contacted"|"accepted"|"replied"|"interested"|"meetings"|"closed";
export type ProofStage = { key: ProofStageKey; label: string; count: number; pct: number | null };
export type ProofLead = { id: string; status: string; source: string; linkedin_invited_at: string|null; linkedin_connected_at: string|null; meeting_booked_at: string|null };
export type ProofInput = {
  leads: ProofLead[];
  sendLeadIds: string[];                           // outreach_sends.lead_id (nulls already dropped)
  replies: { lead_id: string; classification: string | null }[];
  signals: { lead_id: string; kind: string }[];
  observations: { lead_id: string; watch_target: string | null }[];
  watch: { keywords: string[]; competitors: string[]; creators: string[]; hashtags: string[] } | null;
  capped: boolean;
};
export type ProofRow = { key: string; label: string; group: "signal"|"intent"|"other"|"agent"; found: number|null; contacted: number; accepted: number; replied: number; interested: number; closed: number };
export type ProofModel = { funnel: ProofStage[]; sources: ProofRow[]; agents: ProofRow[]; capped: boolean; nonMonotonic: boolean };
// build.ts
export function buildProof(input: ProofInput): ProofModel;
// sources.ts
export function leadSets(input: ProofInput): { contacted: Set<string>; accepted: Set<string>; replied: Set<string>; interested: Set<string>; closed: Set<string> };
export function sourceRows(input: ProofInput, sets: ReturnType<typeof leadSets>): ProofRow[];
export function agentRows(input: ProofInput, sets: ReturnType<typeof leadSets>): ProofRow[];
export function watchCategory(target: string | null, watch: ProofInput["watch"]): "keywords"|"competitors"|"creators"|"hashtags"|"removed"|null;
```
Stage labels: Found · Qualified · Contacted · Accepted · Replied · Interested · Meetings · Closed. `nonMonotonic` is true when any stage count exceeds its predecessor.
